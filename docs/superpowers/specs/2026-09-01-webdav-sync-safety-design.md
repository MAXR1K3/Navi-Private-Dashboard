# Navi WebDAV 同步安全设计

**日期：** 2026-09-01

**状态：** 已批准

**范围：** 长期数据架构的第二个独立子项目

## 1. 目标

在保留 Navi 本地优先、无账号、普通 WebDAV/NAS 文件同步方式的前提下，避免多设备同时编辑造成静默覆盖，并让不同书签上的独立修改能够自动合并。

本阶段完成三件事：

1. 使用 WebDAV ETag 与条件请求关闭“先读取、后覆盖”之间的竞争窗口。
2. 使用上次双方确认一致的数据作为三方合并基准，自动合并互不冲突的书签改动。
3. 使用独立删除墓碑传递删除意图，避免离线旧设备让已删除书签复活。

本阶段不把同步改造成中心服务器、数据库复制协议或 CRDT，也不扩大到凭据隔离和 IndexedDB 主存储迁移。

## 2. 当前风险

当前 `pushWithConflictCheck()` 先 GET 远端并比较书签指纹，再由 `uploadWebdavProfile()` 发出不带条件的 PUT。若另一台设备在 GET 与 PUT 之间修改远端，当前设备仍会覆盖新内容。

当前指纹只覆盖书签的部分字段，不覆盖分类、回收站、日历和设置。它能提示“远端与上次不同”，但无法判断哪一条记录由哪一端修改，也无法安全自动合并。

当前 `mergeRemoteIntoLocal()` 只把本地回收站当作删除标记。远端删除、本地保留的场景会重新上传本地旧记录，使删除失效。UI 回收站还会按 0–14 天清理，不能承担跨设备永久删除语义。

## 3. 已批准的产品行为

- 不同书签上的本地与远端修改自动合并。
- 同一书签在两端发生不同修改时才要求用户选择。
- 删除与另一端对同一书签的编辑同时发生时属于真实冲突，不能自动猜测。
- 第一版完整保护书签、分类、书签顺序和删除；日历与界面设置继续同步，但双方同时修改时整体交给用户选择，不做逐字段自动合并。
- 后台自动上传只能在服务器支持安全条件写入时启用。

## 4. 方案选择

采用 ETag 条件写入、三方合并基准和独立删除墓碑的组合方案。

只增加 ETag 能关闭最后一次写入的竞争窗口，却仍只能整库人工处理冲突；操作日志或 CRDT 则要求重构所有写入、排序和分类路径，超出当前项目需要。三方合并能复用现有稳定书签 ID，并把复杂度限制在同步边界。

这里需要一个同步基准，是因为仅比较“当前本地”和“当前远端”无法区分本地删除、远端新增和双方编辑。Git、版本号、类型、结构校验和普通测试都不能提供浏览器运行时那份共同祖先数据。该基准只参与可逆的合并计算，不是发布门禁；跨系统 PUT 的最终安全性仍由服务器执行 `If-Match` 或 `If-None-Match` 保证。

## 5. 组件边界

### 5.1 `js/sync-merge.js`

新增纯逻辑模块，负责：

- 将 v3/v4 远端文件转换为统一的 canonical snapshot。
- 按稳定 ID 比较 base、local、remote。
- 生成自动合并结果、统计信息和真实冲突列表。
- 合并书签顺序、分类集合与删除墓碑。
- 在用户为冲突项选择本地或远端后生成最终候选状态。

模块不访问 DOM、fetch、localStorage 或 IndexedDB。输入和输出都是普通对象，全部决策可由 Node 逻辑测试覆盖。

### 5.2 `NaviStorage`

在现有 `navi-storage` IndexedDB 中增加 `syncBases` object store，key 为 Profile ID。每条记录包含：

```text
profileId
url
etag
snapshot
savedAt
```

公开异步接口：

```text
NaviStorage.getSyncBase(profileId, url)
NaviStorage.putSyncBase(profileId, url, etag, snapshot)
NaviStorage.clearSyncBase(profileId)
```

Profile URL 改变或 Profile 被删除时清除对应基准。`clearAll()` 同时清除恢复版本与同步基准。基准存入 IndexedDB，避免在约 5 MB 的 localStorage 配额里再复制整份数据。

### 5.3 `js/sync.js`

保留网络与界面编排职责：

- GET 远端原文并读取强 ETag。
- 调用 `sync-merge.js` 计算结果。
- 在无真实冲突时保存本地候选，并通过条件 PUT 更新远端。
- 在有真实冲突时打开冲突界面。
- 处理 412/409、超时、CORS、认证、只读和无 ETag 兼容模式。

现有简单指纹只保留给旧数据诊断或兼容提示，不再作为安全写入依据。

### 5.4 `tools/dav-stub.py`

本地 WebDAV 替身增加：

- 每个文件的强 ETag。
- `If-Match` 与 `If-None-Match: *` 检查。
- 412 Precondition Failed。
- 在客户端 GET 后、PUT 前注入另一设备写入的竞争故障。
- 缺失 ETag 和弱 ETag 的兼容性故障。
- 请求记录中的 ETag 和条件头证据。

## 6. v4 同步数据格式

`bookmarks.json` 继续使用 `schema: "navi-bookmarks"`，版本升级为 4：

```json
{
  "schema": "navi-bookmarks",
  "version": 4,
  "bookmarks": [
    {
      "id": "b123",
      "title": "Example",
      "url": "https://example.com",
      "category": "Work",
      "description": "",
      "tags": [],
      "favorite": false,
      "updatedAt": 1788278400000
    }
  ],
  "categories": ["Work"],
  "trash": [],
  "calendarEvents": [],
  "theme": "light",
  "view": "grid",
  "settings": {},
  "sync": {
    "protocol": 1,
    "tombstones": [
      {"id": "b-old", "deletedAt": 1788278500000}
    ]
  }
}
```

`updatedAt` 用于诊断、展示和迁移，但不依赖设备时钟自动决定冲突胜负。权威判断来自与 base 的结构比较。

本地主状态使用根级 `syncMeta: { tombstones: [] }` 保存当前 Profile 的墓碑；现有 `navi.pdata.<id>` Profile 缓存也必须保存该字段。远端序列化时把它映射为上例的 `sync.tombstones`，避免把传输协议字段散落进普通设置。

书签内容字段包括 `id`、URL、标题、分类、描述、标签和收藏状态。`clicks` 与 `lastOpened` 作为设备活动统计，合并时取较大值，不触发内容冲突。未知字段在不破坏校验的前提下保留。

墓碑与 UI 回收站分离。任何保存导致某个已存在书签 ID 消失时都创建或保留墓碑；同一 ID 被恢复时移除墓碑并更新书签。第一版不自动清理墓碑，避免长期离线设备重新引入旧记录。墓碑体积后续如确有增长问题，再设计带设备确认的压缩机制。

## 7. 兼容与迁移

- v3 文件和没有 `sync` 元数据的合法旧文件继续可读。
- 旧书签缺少 ID 时，规范化阶段生成稳定 ID；在首次明确、安全的 v4 写回后固化。
- 旧数据缺少 `updatedAt` 时使用 `0`，不能据此覆盖有冲突的数据。
- 首次连接已有远端文件但没有同步基准时，不自动合并或上传。用户必须先选择远端、本地或显式合并，以建立共同基准。
- 已有 Profile 只有 `remoteFp` 而没有 base 时也按首次建立关系处理，不能把旧指纹当作三方基准。
- v4 文件仍能由旧版 Navi 读取书签主体；旧版会忽略新增 `sync` 字段。升级后的客户端不得假设旧版客户端遵守墓碑，因此条件写入和合并仍是必要保护。
- 已存在 v4 base 时若远端退回 v3，视为协议降级冲突，不自动接受或上传。旧版客户端的无条件写入无法由新版网页从客户端侧完全阻止；安全能力要求所有具备远端写权限的 Navi 客户端升级。

## 8. 本地变更跟踪

由统一保存边界比较保存前后的书签映射：

- 新书签或内容字段变化时写入新的 `updatedAt`。
- 已有 ID 消失时创建墓碑，即使 UI 回收站设置为“立即删除”。
- 已删除 ID 恢复时移除墓碑并更新时间。
- 仅点击次数或最后打开时间变化不更新时间。

同步远端数据或完成冲突选择时，以明确的“应用远端候选”入口保存，避免把远端变化误标记成本地编辑。Chrome/Safari 导入、批量操作、分类重命名和恢复动作仍可沿用现有 `save()`，因为变化识别发生在统一边界，而不是散落到每个按钮处理器。

每个 Profile 的书签数据、墓碑和本地同步元数据随现有 Profile 缓存一起切换；不同 Profile 之间不得共享墓碑或 base。

## 9. 三方合并规则

输入为 base、local、remote 三份 canonical snapshot。

### 9.1 书签记录

按 ID 独立判断：

| 本地相对 base | 远端相对 base | 结果 |
| --- | --- | --- |
| 未变 | 未变 | 保留任一相同版本 |
| 修改 | 未变 | 采用本地 |
| 未变 | 修改 | 采用远端 |
| 修改为相同内容 | 修改为相同内容 | 自动采用共同内容 |
| 修改为不同内容 | 修改为不同内容 | 真实冲突 |
| 删除 | 未变 | 自动删除并保留墓碑 |
| 未变 | 删除 | 自动删除并保留墓碑 |
| 删除 | 修改 | 真实冲突 |
| 修改 | 删除 | 真实冲突 |
| 两端分别新增不同 ID | — | 两条都保留 |
| 两端新增同一 ID 且内容不同 | — | 真实冲突 |

冲突选择只作用于对应 ID。用户选择保留书签时移除该 ID 的墓碑；选择删除时保留墓碑。

### 9.2 顺序

书签数组顺序作为单独的 ordered ID list 比较：

- 只有一端相对 base 改序时采用该端顺序；不在该序列中的另一端新增 ID 按另一端出现顺序追加到末尾。
- 两端都没有改序时沿用 base，先按本地出现顺序追加本地新增 ID，再按远端出现顺序追加尚未出现的远端新增 ID。
- 两端产生完全相同的顺序时直接采用。
- 两端都进行了不同改序时产生一个“书签顺序”集合冲突，让用户选择本地或远端顺序；书签内容仍可自动合并。

### 9.3 分类

书签的分类归属随书签记录合并。显式空分类作为分类集合处理：单边新增自动保留；单边删除且另一端未变自动删除；双方对分类集合做不同修改时产生一个集合冲突。最终运行现有分类去重和归一化。

### 9.4 日历与设置

第一版将 `calendarEvents` 作为一个整体字段，将 `theme`、`view` 和经过现有隐私合并后的 `settings` 作为一个设置组：

- 只有一端相对 base 改变时自动采用改变的一端。
- 两端变化结果相同则直接采用。
- 两端变化不同则分别产生“日历”和“界面设置”集合冲突。

AI Key、WebDAV 密码和 Profile 配置继续遵守现有 `preservePrivate`、`preserveProfiles` 与脱敏规则，不进入远端冲突内容。

## 10. 安全写入流程

### 10.1 读取和建立基准

1. GET 远端，保留原始文本、HTTP 状态和 `ETag`。
2. 只有强 ETag 可用于 `If-Match`；缺失或以 `W/` 开头的弱 ETag进入兼容模式。
3. 解析、规范化并验证远端数据。无效原文不能进入合并。
4. 读取与当前 Profile ID、URL 同时匹配的 base。
5. 没有 base 时执行首次建立关系流程；不能静默把本地或远端当作共同祖先。

首次建立关系提供三个明确动作：采用远端、用本地条件覆盖远端、预览首次合并。首次合并只对不同稳定 ID 或不同规范化 URL 的书签取并集；同 ID 或同 URL 内容不同、任一端存在无法解释的墓碑时列为冲突。完成选择并使本地、远端一致后，才保存第一份 base。

### 10.2 自动合并与写回

1. 计算三方合并。
2. 如果没有真实冲突，先验证并保存本地候选；保存失败时不得写远端。
3. 如果合并结果与远端不同，使用本次 GET 的 ETag 发出 `PUT If-Match: <etag>`。
4. 如果远端不存在，使用 `PUT If-None-Match: *` 创建。
5. PUT 成功后，以服务器返回的新 ETag 建立 base；若成功响应未返回 ETag，则立即 GET 校验实际远端内容并获取 ETag。复读仍没有强 ETag 时可保存 snapshot 供后续人工比较，但 Profile 必须进入兼容模式。
6. 本地状态、远端内容和 base 都确认一致后才显示“同步完成”。

### 10.3 并发重试

服务器返回 409 或 412 表示计算完成后远端又被修改。客户端重新 GET、重新计算三方合并，最多进行 3 次有进展的条件写入尝试。再次出现真实冲突或连续竞争时显示冲突界面，不降级为无条件 PUT。

用户在冲突界面选择“使用本地”只代表内容选择，不授权绕过 ETag。客户端仍需基于最新强 ETag 条件写入；写入前再次变化时重新检查。

## 11. 无 ETag 兼容模式

若服务器不返回强 ETag：

- 停止后台自动上传，不改变用户保存的偏好，但在界面显示“服务器不支持安全自动写入”。
- 允许继续拉取和使用本地缓存。
- 手动上传必须先展示明确确认，说明服务器无法保证并发写入安全，并在上传前重新读取远端进行现有内容检查。
- 兼容模式不得显示“安全同步”或把普通 PUT 结果当作无冲突证明。
- 一旦服务器开始返回强 ETag，下一次成功拉取即可重新建立安全模式。

不使用内容哈希冒充服务器条件写入。客户端哈希或指纹无法阻止另一台设备在检查后、PUT 前修改文件。

## 12. 冲突界面

替换当前只显示书签数量的整库冲突弹窗：

- 顶部显示已自动合并的新增、修改、删除数量。
- 仅列出真实冲突；每项展示名称、URL以及“本地 / 远端 / 已删除”的差异摘要。
- 每项必须明确选择本地或远端，提供“全部使用本地”“全部使用远端”快捷动作。
- 顺序、分类、日历和设置冲突以独立集合项显示。
- 主按钮为“应用选择并安全同步”，在所有冲突有选择前禁用。
- 保留取消操作；取消不会改变本地或远端。
- 无法解析的远端原文不提供自动合并，可下载远端原文、取消，或明确选择用本地覆盖；覆盖仍使用当前 ETag。

弹窗沿用现有具名 dialog、初始焦点、Tab 焦点陷阱和焦点归还规则。状态变化通过 live region 宣告。危险的整库覆盖不作为默认高亮动作。

## 13. 错误和恢复

- 远端解析失败：不修改本地，不更新 base，不自动覆盖。
- 本地候选验证或保存失败：不发 PUT。
- PUT 超时或网络失败：本地候选可以保留，但 base 不前移；下次同步重新与原 base 合并。
- PUT 成功而 base 写入 IndexedDB 失败：远端与本地保持新状态，显示“同步完成，但安全基准未保存”；下次操作进入保守的首次建立关系流程。
- IndexedDB 不可用：允许读取远端，但禁用自动合并上传；不得把 `remoteFp` 当替代 base。
- 认证、只读、CORS 和混合内容继续使用现有具体错误诊断。
- 412/409 永远不转换为“上传成功”。
- 应用任何远端或冲突结果前保留现有恢复版本，确保误选仍可恢复。

## 14. 测试策略

严格使用 RED → GREEN。

### 14.1 纯逻辑测试

- v3/v4 规范化和非法数据拒绝。
- 全部书签三方合并矩阵，包括新增、新增同 ID、修改、删除、删除对编辑。
- tombstone 优先和恢复移除墓碑。
- 点击统计不制造内容冲突。
- 单边改序、同序、双边不同改序。
- 分类集合、日历和设置组的单边/双边决策。
- Profile ID 相同但 URL 不同不能复用 base。
- 缺失 base、缺失/弱 ETag、404 和有效强 ETag 的传输决策。
- 412/409 重试达到上限后不允许无条件上传。

### 14.2 WebDAV 协议测试

使用升级后的 stub 断言：

- GET 返回并暴露强 ETag。
- 正确 `If-Match` PUT 成功并返回新 ETag。
- 旧 ETag 返回 412且存储内容不变。
- `If-None-Match: *` 只在文件不存在时成功。
- CORS 允许 `If-Match`、`If-None-Match` 并暴露 `ETag`。
- 无 ETag 和弱 ETag 时进入兼容状态。

### 14.3 双客户端真实浏览器 E2E

使用两个隔离 Chrome profile 连接同一个本地 WebDAV stub：

1. 两端建立同一 base。
2. A、B 分别新增不同书签，最终远端同时包含两条。
3. A 删除一条、B 修改另一条，最终删除不复活且修改保留。
4. A、B 修改同一书签，B 显示逐项冲突且远端不被提前覆盖。
5. 在 B 的 GET 与 PUT 之间注入第三方写入，第一次 PUT 收到 412，重新合并后不丢第三方内容。
6. 服务器无 ETag 时自动上传被抑制，手动兼容上传显示警告。
7. 取消冲突界面后本地和远端均保持原样。

- `sw.js`、`README.md`：缓存版本、同步要求和故障说明。

实际计划可在保持边界的前提下调整文件拆分，但不得把合并纯逻辑重新塞回 DOM 或网络编排代码。

## 16. 明确不在本阶段完成

- API Key、WebDAV 和 Synology 凭据隔离。
- IndexedDB 成为主数据唯一来源。
- 日历逐记录合并和设置逐字段合并。
- CRDT、中心协调服务或设备注册协议。
- 自动清理删除墓碑。
- 与浏览器原生书签的双向回写。

## 17. 完成标准

- 支持 ETag 的服务器上不存在无条件正常 PUT。
- GET 与 PUT 之间的远端变化由 412/409 捕获，并重新合并或交给用户。
- 不同书签上的并发修改自动合并。
- 同一书签的不同修改和删除对编辑不会被静默猜测。
- 远端或本地删除不会被另一端未修改的旧记录复活。
- 无 ETag、无 base、IndexedDB 失败和无效远端都进入明确的保守路径。
- v3 远端继续可读，v4 写回只发生在安全或明确授权的流程中。
- 冲突界面可访问、可取消，未作完整选择时不能提交。
- 所有逻辑、协议、双客户端浏览器和现有回归测试通过。
